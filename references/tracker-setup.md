# Tracker setup

The procedure the `setup-playbook-profile`, `new`, and `adopt` skills follow to write a tracker doc. Read "Trackers" in `references/conventions.md` first: it defines the doc's sections, the Layout roles, and the Wayfinding operations. Paths here are relative to the plugin's root folder.

## Which doc

- The user's default tracker (from the `setup-playbook-profile` skill): `trackers/<kind>.md` in the folder that holds the profile file. It never goes inside a project's repository.
- No profile, and the work is in a repository: `docs/tracker.md` in that repository. It needs no profile and no `project.yaml`.
- A project's own doc (from `new` or `adopt`): `docs/tracker.md` in the project. Write one when the project is shared, when its tracker kind differs from the profile's default, or when the user says the default doc's Layout does not fit it (another location, other statuses, other rules). Otherwise the project uses the user's doc for its kind: make sure that doc exists, and run this setup for it when it does not.
- A project with a primary and a secondary tracker gets one `docs/tracker.md` covering both, in the two-tracker shape the conventions give.

## Steps

1. **Pick the template.** The kind is `project.yaml` `tracking` or the profile's `tracker.kind`; ask when neither names one, listing the shipped templates in `references/trackers/` (`todoist`, `openproject`, `github`, `markdown`) and offering `blank` for any other tracker. A user with no tracker yet gets `markdown`, which needs nothing installed. Use `references/trackers/<kind>.md`, or `blank.md` with every Mechanics label (Tool, Find by name, Fetch, Comment, Change status, Assign, Create, Edit, Link parent and child, Link blocking, Quirks) filled in from the tracker's own documentation and tested. Test the read operations (Find by name, Fetch) freely. Try an operation that would create or change something in the tracker only with the user's yes, on a ticket the user names or on a clearly labelled test ticket the user agrees to. The `markdown` kind needs no tool: its tickets are files in the repository.
2. **When the doc already exists**, this is an update in place. Keep every hand edit: change only the lines the user agrees to, and never rewrite House rules. Compare the doc's Mechanics with the current template line by line (quirks included) and propose each difference; take it on a yes.
3. **Read the live tracker** where a tool for it is connected, reading only: its places (projects, sections, boards) and their descriptions, statuses (which are closed), types, labels or categories, the current user, and whether parent and blocking links work. **Check each read operation** of the template's Mechanics (Find by name, Fetch, listing children, reading blocking links, a filtered list) by running it once against the connected tool. The template describes the tracker in general; where the connected tool names an operation differently, lacks one, or behaves otherwise (a filter that cannot be combined with a place, a text search that is a separate call, results that come in pages), correct that line in the user's copy and say what changed. When nothing is reachable, say so and fill the Layout from the user's answers. Any Layout line you infer rather than read (a capture place, a starting status) is put to the user to confirm; never leave it marked as assumed.
4. **Propose the Layout.** Fill every role from what the tracker holds, in its own query language where it has one: Where, Pickable work, Ranking, Excluded, New ticket, Start, Note, Done, Stopped partway, Cannot proceed, Not worth doing, Parent and children, Blocking, Close the parent. Leave a role empty when the step does not exist there; never invent one. For a project, `Where` is its location (`ref` in `tracking`). When the tracker has several closed statuses, ask once which one Done, Not worth doing, and an out-of-scope question each use, and record the answer in those roles. **Propose house rules** from what the tracker shows (a section or label that holds ideas rather than commitments, an inbox of unsorted captures, statuses for work not yet agreed, a container type never worked itself), each with what it is based on; the user keeps, changes, or drops each.
5. **Propose the Wayfinding operations** (Map, Child ticket, Type marker, Claim, Frontier query, Resolve) from the template's defaults. A map's home is a place for committed work: never an inbox or another capture place that is swept for sorting. When no place is clearly right, ask. Some defaults need something to exist in the tracker first: a label, a category, a type, or a claim marker. Check which already exist, and list the ones that would have to be created and how (through the tool, or by hand in the tracker's own settings where the tool cannot). Create nothing without the user's yes. When the user says no, or the item can only be made by hand and the user does not make it, use the template's fallback that needs nothing created: title or subject prefixes such as `[map]`, `[research]`, `[prototype]`, `[grilling]`, and `[task]` as the markers, and the template's fallback claim. With the prefixes, add them to Excluded (and to the Pickable work query where its language can express it), so map and question tickets are never offered as work. Where the template gives no fallback, leave that operation empty and say the `wayfinder` skill cannot work a map in this tracker until it is filled. Record in the doc which form is in use. Show the whole proposed doc.
6. **Run the pickable work query** and show the result. Read every page of it. Say how many tickets the query returned, how many each of Excluded, the house rules, and blocking took out, and how many are left; then list the first ten or so left, by title, in Ranking order. The count is shown, not written into the doc. Adjust the Layout with the user until the result is what they would expect to be offered.
7. **Write the doc** on the user's yes, in the template's headings and order, after creating any item from step 5 the user agreed to.
   - A user-level doc is written beside the profile; nothing in any repository changes.
   - `docs/tracker.md` follows the project's rules for added files: committed with the other standard files in the user's own repo, through review in a shared repo the user leads, and listed in the local exclude file in a repo someone else owns. A shared project's doc holds only what is true for everyone who uses the repo: no personal details and no machine paths, and the user sees its exact text first.
8. **Record the kind.** When `project.yaml` exists and the project's tracker is not the profile's default, or its location is known, set `tracking` in it (`primary`, and `secondary` with its `tickets`) to match the doc.

## Run with no one to answer

When setup runs where the user cannot answer (a subagent, a batch or scheduled run), it writes nothing and creates nothing. It returns the proposed doc, the pickable work result, the Mechanics corrections from step 3, and every question it would have asked, each with the answer it would propose and what that answer rests on.
